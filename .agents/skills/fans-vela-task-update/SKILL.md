# VELA 应用更新内容

从任务详情链接的 `id` 或用户提供的任务编号定位任务，使用当前 VELA CLI 会话执行 `vela task get <任务编号> --json`。从 `applications` 读取每条关联的 `id`、`appId`、`appName`、`version`、`submitGitBranch`、`submitGitCommit` 和 `updateContent`。用户指定应用时只处理指定的关联。用户只问任务详情时回答对应问题。只发链接或要求起草时，生成预览。CLI 命令缺失时检查 `vela task app --help`，会话失效时提示用 `vela login` 扫码。

## 核对 Git 比较范围

1. 优先检查当前项目和可访问的相关工作区。用用户提供的仓库路径、VELA 应用的 Git 地址或已有项目映射定位仓库，核对 Git remote。只有仓库名、应用名和提测分支等证据能确认唯一映射时才按名称匹配。多个应用共用仓库时，核对各自的包路径和共用模块。如果未找到对得上的仓库，可从 VELA 应用详情或该应用的「查看Git提交日志」补充线索。
2. 优先以 VELA 的 `submitGitCommit` 为终点，将缩写解析为唯一完整 SHA，提测分支用于核对来源。本地引用不足时，从已核实且可访问的远端获取相关分支或标签。没有本地副本时可以查看该远端的代码比较，或使用临时克隆。没有提测提交时，仅在证据表明分支对应当前迭代的情况下使用核对后的分支 HEAD，并在预览中标注来源。共享分支（如 `dev`）需要已知提测提交或其他可证实的迭代截止点。
3. 用户明确指定范围时按指定的基线核对。否则优先查同一应用对应上一版的发布或提测记录、能确认对应的版本标签。独立迭代分支可以用已证实的集成目标与分支分叉点作为基线。核对两个端点和历史关系。基线或终点有歧义时，列出待核对的提交、版本或仓库，并继续处理范围明确的其他应用。日期、版本号和提交标题可以辅助判断，单独使用时不足以确定范围。
4. 用 `git log <基线>..<终点>` 查提交背景，用 `git diff --name-status <基线> <终点>` 和具体 diff 确认实际变化。用 Git 引用直接比较，保留工作区现状。多包仓库需要同时检查应用路径与实际影响它的共用代码。确认哪些行为会变，再把结果和 VELA 任务中的描述或计划对应起来。

## 起草并预览

每个应用分别写正文，以「更新内容」「影响模块」「测试要点」组织。描述可从代码证实的行为变化、影响的页面或接口，以及测试人员能执行的操作和预期结果。配置、数据库或接口兼容性变化有证据时写明。既有正文中仍适用的背景或测试提醒应保留；存在冲突时在预览中指出。把建议的测试步骤写成待验证事项。

对代码范围已核实的应用，用 `vela task app update <任务编号> --app-id <应用ID> --content "$content" --json` 生成预览。传 `appId`，并用返回的 `appUpdate.associationId` 核对关联 ID。多行正文作为一个参数传递，保持换行。保留每个应用的完整正文、`previewId` 和所用 Git 提交。

一次展示本次拟写回的应用、版本、提测分支、基线和终点，以及原文和拟写入的完整正文。有缺口的应用注明阻塞原因，需要用户补充时给出具体应用和缺少的证据。`APP_CONTENT_UNCHANGED` 表示已有正文相同，汇报为无需写入。

## 确认后写入

用户确认本次预览后，重新查询任务，核对关联 ID、版本、提测分支、提测提交和原正文。终点来自分支 HEAD 时，再核对该引用解析的 SHA。变化的应用重新生成预览，确认后再提交。

用预览时相同的任务编号、`--app-id` 和 `--content`，逐个加 `--apply <previewId>`。只有返回 `submitted: true` 或后续回查到同一关联的正文符合预览，才报告写入已核实。`PREVIEW_STALE` 时重新读取和预览，`SUBMIT_UNCERTAIN` 时先用 `vela task get <任务编号> --json` 回查同一关联。最后按应用报告已写入并核实、已是目标正文或未能写入及原因。写入范围限于用户确认过的应用更新内容。
